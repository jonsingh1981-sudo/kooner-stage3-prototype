# Kooner Fleet Management System — Stage 6 Backend / Shared Platform

Stage 6 puts a real shared PostgreSQL/API platform underneath the approved Stage 3–5 interfaces. It does **not** redesign the approved Kooner operation and it does **not** connect live external providers.

## Architecture

- Existing repository remains the single Kooner codebase.
- `server/` contains the Node/Express API, authentication, permissions, business rules, sync and compatibility services.
- `server/migrations/` contains version-controlled PostgreSQL migrations.
- `server/seed.js` creates the controlled Stage 1–5 regression scenarios and Stage 6 test users.
- PostgreSQL is the intended authoritative system of record.
- `stage6-client.js` is a temporary compatibility bridge that lets the approved Stage 3–5 screens use API/database-backed state while the front-end storage calls are progressively retired.
- If the Stage 6 API cannot be reached, the acceptance environment must fail closed rather than silently treat legacy browser business data as authoritative. Technician offline operation is the controlled exception.

## Render deployment

The repository includes `render.yaml` for a Stage 6 Web/API service. It references the existing Render Postgres database `kooner-stage6-postgres` using Render's `fromDatabase.connectionString` mechanism so the database password is never committed to source control.

Required service environment values:

- `NODE_ENV=production`
- `APP_ENV=stage6-test` while Stage 6 is under acceptance test
- `DATABASE_URL` — linked from Render Postgres, not hard-coded
- `TEST_USER_PASSWORD` — test-only secret, supplied in Render
- `MFA_ENCRYPTION_KEY` — generated/stored as a Render secret
- `SESSION_SECRET` — generated/stored as a Render secret

The application runs migrations and the idempotent test seed during startup, then listens on Render's `PORT`.

## Security controls in the Stage 6 foundation

- Passwords are stored as salted scrypt hashes.
- Sessions use random tokens; only token hashes are stored server-side.
- Customer/Site permissions are resolved server-side.
- CSRF checks protect authenticated write routes where applicable.
- Sensitive routes use permissions, request size limits and rate limiting.
- SQL is parameterised.
- Optimistic versions prevent silent stale writes.
- idempotency keys / unique sync event IDs protect against duplicate application.
- internal-only financial/cost/document data is excluded from customer scope.
- audit events are generated by the server for controlled actions.
- external penetration testing remains a production dependency and Stage 6 does not claim formal security certification.

## DCR build control

DCR-089 through DCR-115 live in shared backend storage. Stage 6 items remain `Building` until the deployed environment has genuine acceptance evidence. DCR-108 and DCR-115 remain deferred production dependencies. `Ready to Test` must not be assigned merely because code exists in the repository.

## Acceptance proof required before Stage 6 sign-off

1. Operations changes a Work Order and an independent Technician session retrieves the same backend Attendance.
2. Technician changes Attendance/work and Operations receives the same server-backed state.
3. Operations issues an Estimate and an authorised Customer session receives the same Estimate.
4. Customer approval returns to Operations with the same approval/audit record.
5. API-level Customer/Site/role boundaries pass.
6. stale concurrent update returns a conflict instead of silently overwriting.
7. the same offline sync event submitted twice is applied once only.
8. records survive browser clearing and application redeploy.
9. Stage 3–5 regression journeys remain functional.

## Development/Test reset

Migrations and seed are idempotent. The Stage 6 test database can be recreated by using an authorised development/test reset procedure or by resetting the non-production database and restarting the service. A production environment must never expose a casual reset path.

## External integrations

DVLA, DVSA, telematics, accounting, M365/email, SMS, customer APIs, fuel cards, parts suppliers, mapping and payment providers remain **Future Integration – Not Connected** during Stage 6.

## Stage boundary
